## 배경

우아한테크코스 프리코스의 오픈미션으로 진행한 프로젝트입니다. 수강신청 때마다 서버가 다운되는 것을 보며 "서버를 늘려야 할까, 큐로 요청을 제한해야 할까"가 늘 궁금했고, 다른 사람의 설명이 아니라 직접 재현해 수치로 확인해 보고 싶었습니다.

## 구조와 구현

- **구성**: 요청은 k6 → WebFlux 라운드로빈 로드밸런서(:8080) → 서버 3대(:8081~8083) → PostgreSQL 순서로 흐릅니다. 서버마다 DB를 따로 두면 락 경합을 관찰할 수 없기 때문에, 일부러 세 서버가 DB 하나를 공유하게 했습니다.
- **접근 제어**: 요청을 우선순위 큐에 넣고 동시에 처리하는 수를 제한했습니다. 처음에는 고정값을 사용했지만, 이후 응답 지연을 기준으로 여유가 있으면 조금씩 늘리고 과부하가 감지되면 줄이는 적응형 방식으로 바꿨습니다.
- **측정 오류 추적**: 한동안 k6가 모든 응답을 에러로 집계했습니다. 원인을 추적해 보니 로드밸런서가 백엔드 응답 헤더를 그대로 전달해 헤더가 중복으로 붙고 있었고, exchangeToMono로 바디만 전달하도록 고친 뒤에야 측정값을 신뢰할 수 있었습니다.

## 결과 (k6 실측)

수강 등록 API에 60초 동안 초당 2,000건의 요청을 보냈습니다(VU 1,000~5,000, 통과 기준은 p95 500ms 미만·실패율 1% 미만).

| 지표 | 고정 동시성 | 적응형 동시성 |
| --- | --- | --- |
| 실패율 | 20.79% | **0%** |
| p95 응답 시간 | 11.71s | **462ms** |
| 처리량 | 초당 1,221건 | **초당 1,982건** |
| 통과 기준 | 미달 | **통과** |

- 초당 200건일 때는 p95 21ms, 실패율 0%였고, 조회 API는 VU 100에서 p95 27ms로 초당 878건을 처리했습니다.
- 정원 100명인 강좌에 요청을 집중시켜도 DB의 수강 인원은 정확히 100명으로 유지되어, 정원을 초과한 등록은 발생하지 않았습니다.
