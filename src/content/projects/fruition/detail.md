## 해결하려던 문제

문서는 PDF, 워드, 한글, 노션, 메모 앱처럼 여러 형식과 도구에 흩어져 있습니다.\
기존 문서 관리는 파일명/폴더/태그에 기대기 때문에, 내용 일부나 작성 맥락만 기억나면 결국 문서를 하나씩 열어 확인해야 합니다.\
저장 공간이 커질수록 분류/연결/중복 정리/최신화 부담도 사용자에게 남아, 자료가 지식이 되지 못하고 쌓이기만 합니다.

RAG는 질문할 때마다 원본에서 관련 조각을 처음부터 찾아오기 때문에, 여러 문서에 걸친 맥락을 통합하거나 지식을 키워 가지는 못하고 같은 답변에 대답하기 위해 계속해서 데이터를 읽어내야 합니다.\
이런 문제를 해결하려던 도중 안드레 카파시가 제시한 **LLM Wiki** 개념을 활용하면 새 자료가 들어올 때 마다 기존 위키와 비교해 관련 항목을 연결하고 내용을 갱신하여 LLM이 읽고 활용하기 좋은 형태로 문서를 관리할 수 있을거라 생각하여 이 개념을 적용한 프로젝트를 수행하기로 했습니다.

## 내가 맡은 부분

- **팀장/기획**: 마일스톤과 개발 일정, 배포를 관리하고 1주 단위 스프린트와 회고로 목표와 진행 상황을 조절했습니다.\
  기획심의의 "MVP가 너무 넓다"는 의견을 반영해 LLM Wiki 생성과 자연어 검색부터 만들고, PoC 이후 나머지 기능의 순서를 정했습니다.\
  마크다운을 제외한 확장자 중에서 가장 널리 사용되는 PDF는 범위내에 포함시키고, PDF는 텍스트/마크다운 지원 이후 Converter로 확장하도록 범위를 조정했습니다.\
  이후 실사용자를 모으고 받은 피드백을 기능 개선 항목으로 정리했습니다.
- **아키텍처**: 모놀리스와 MSA 두 구조를 k6를 활용한 부하 테스트로 비교하고 MSA구조를 택하여, 백엔드 서버를 인증과 문서 서비스를 분리했고, AI 작업은 Kafka 기반 비동기 실행과 전용 워커로 분리했습니다.
- **프론트엔드**: 디자이너와 화면 구조를 정하고 Next.js/React/TypeScript로 `GitHub Flavored Markdown` 편집기, 지식 그래프 뷰, 채팅 답변을 Wiki에 추가하는 기능을 만들었습니다.
- **Notion 데이터 이전**: Notion의 내보내기 기능을 통해 생성된 zip을 분석해 하위 페이지는 폴더로, 본문/이미지/표/PDF/문서 간 링크는 그대로 옮기는 가져오기 기능을 화면과 서버 모두 만들었습니다.\
  가져오기 세션 API로 실패한 항목을 다시 시도할 수 있게 하고, 가져온 문서는 예상 비용을 확인한 뒤 PDF 변환과 Wiki 편입 여부를 고르도록 했습니다.
- **인프라/배포**: Terraform으로 AWS EKS 인프라를 구성하고 GitHub Actions OIDC 배포를 자동화했습니다.\
  인증 DB/Redis 이중화, 절전/자동 기동, 모니터링과 비용 알림을 구현했습니다.
- **AI 개발 환경**: 팀 공통 개발 규칙과 프로젝트 맥락을 문서로 정리하고 반복 작업은 공용 스킬로 공유했습니다.\
  AI를 활용하여 빠르게 코드를 생성하면서도, 생성한 코드에 대해 리뷰와 테스트를 수행하여 원하는 작업을 제대로 수행하는 경우에만 반영하도록 했습니다.

## 문제 해결과 결과

### AI 요청이 몰리면 로그인까지 멈추는 문제

모든 기능을 하나의 서버에서 처리하는 모놀리스와, 인증/문서 서비스를 나눈 MSA를 두 구조를 비교했습니다.\
로컬 머신 한 대에서 실제 LLM 대신 응답을 흉내 내는 모의 LLM을 사용하고, k6로 두 구조에 같은 부하를 보냈습니다.\
평상시에는 가상 사용자(VU)를 10→50→100명으로 늘렸고, 요청 폭주 시에는 AI 100 VU와 일반 API 20 VU를 동시에 실행했습니다.\

| 시나리오 | 모놀리스 | MSA |
| --- | --- | --- |
| 평상시 (VU 10→50→100, 8분 × 2회) | 초당 218.9건 · 실패 0% · p95 22.6ms | 초당 217.4건 · 실패 0% · p95 22.2ms |
| AI 요청 폭주 (AI 100 VU + 일반 20 VU) | 일반 API 실패율 26.45% · 인증 응답 중앙값 9,981ms · 로그인 불가 | 일반 API 실패율 16.67% · 인증 응답 중앙값 7.15ms · 로그인 83ms |
| 10분 이상의 AI 작업 30건 동시 실행 | 22건 접수 후 모두 실패 | 30건 모두 접수 · 실패 0 · 워커 6대가 차례로 처리 |

모놀리스는 AI 작업이 서버의 요청 처리 스레드를 모두 차지해 로그인 요청까지 처리하지 못했습니다.\
오래 걸리는 작업에서는 AI 응답을 기다리는 동안에도 DB 연결을 계속 붙잡고 있어, 다른 요청이 쓸 수 있는 연결이 모두 소진됐습니다.\
작업이 끝나기 전에 코드에 고정된 5분 제한 시간에 걸려 중단되는 문제도 있었습니다.

이 문제를 해결하기 위해 MSA 구조를 택하기로 했고, 인증과 문서 서비스를 나누고, AI 작업은 Kafka 메시지 큐에 넣어 별도의 작업 처리 서버가 맡도록 바꿨습니다.\
이 결과로 AI 부하가 몰려도 인증 응답 중앙값이 9,981ms에서 <strong>7.15ms</strong>로 유지됐고, 10분 이상의 AI 작업 30건도 문제없이 모두 처리됐습니다.\
뿐만 아니라 장애 전파를 확인하기 위한 인증 서비스를 중단한 별도 실험에서도, 권한 정보를 300초 동안 임시 저장해 둔 덕분에 문서 조회와 생성이 정상 처리됐습니다.

### 월 예산 안에서 가용성과 비용 조정

월 예산은 400\~650달러였습니다.\
로그인이 막히면 서비스를 쓸 수 없어 인증 DB는 Multi-AZ, Redis는 자동 장애조치가 가능한 2노드로 구성했습니다.\
문서/AI 코어 DB는 테스트 단계에선 Single-AZ로 두고 실제 사용자 데이터를 받기 전에 Multi-AZ로 전환하기로 했습니다.

NAT 게이트웨이는 1대, AI 워커에는 스팟 노드를 사용했습니다.\
실행 중인 작업이 없을 때 절전 모드로 전환하면 일반/AI 노드그룹을 0대로 줄이고, Fargate에 남겨 둔 화면에서 접속을 받아 다시 기동합니다.\
EventBridge → request-wake Lambda가 일반 노드 2대와 AI 노드 1대를 기동하며, 상태를 DynamoDB에 기록해 중간 실패 시 다음 실행에서 복구하도록 했습니다.

### 기밀 문서를 맡길 수 있는 보안

중간점검에서 "기밀성이 보장되어야 하는 문서의 보안 대책이 필요하다"는 의견을 받았습니다.\
모든 통신은 TLS로 암호화하고, 문서 원본은 전용 키로 암호화한 비공개 저장소에, DB/캐시/디스크도 암호화해 사설망에 두었습니다.\
모든 문서 요청은 서버에서 워크스페이스 멤버십과 문서/폴더 권한을 검사합니다.\
로그인 토큰은 access 토큰 15분, refresh 토큰 14일로 짧게 두고 refresh 토큰은 쓸 때마다 새로 발급하며, WAF로 IP당 5분 3,000회까지 요청을 제한합니다.

## 서비스 구성과 기능

![Fruition AWS 인프라 구성도](/img/fruition/architecture.webp)

사용자는 웹 SaaS([fruition.wiki](https://fruition.wiki/))로 Fruition을 이용합니다.\
외부 요청은 WAF → ALB를 거쳐 서울 리전 가용영역 2개에 걸친 EKS 프라이빗 클러스터로 들어갑니다.

**인프라 구성**

- **서비스 분리**
  - access-svc(인증)와 document-svc(문서) 분리
  - 서비스별 RDS(PostgreSQL) 2대
- **프론트엔드**
  - Next.js, EKS Fargate Pod 2개 (0.25 vCPU / 768Mi)
  - 노드를 0대로 내린 절전 중에도 화면 유지
- **노드**
  - 일반: t3.large 온디맨드 2\~5대 (API, Kafka)
  - AI: m5/m5d/m6i/m7i xlarge 스팟 0\~4대
  - AI 노드에 taint 적용하여, AI 작업만 배치
- **오토스케일링**
  - API: HPA, CPU 70% 기준 Pod 2\~4개
  - AI 워커: KEDA, Kafka lag 기준 Pod 1\~4개
  - 노드: Cluster Autoscaler
- **네트워크**
  - 서울 리전, 가용영역 2개
  - 서버와 DB는 프라이빗 서브넷에 배치
  - WAF(IP당 5분 3,000회 제한) → ALB(주소/경로별 분기)
  - EKS API 프라이빗, NAT 게이트웨이 1대
- **데이터**
  - RDS: db.t4g.small, 인증 DB Multi-AZ / 코어 DB Single-AZ, 백업 7일
  - Redis: cache.t4g.micro 2대, 자동 장애조치
  - RDS/Redis/S3 저장 암호화, 통신 TLS
- **권한과 시크릿**
  - Redis: 서비스별 ACL
  - S3: IRSA(Pod별 IAM 역할)
  - 시크릿: Secrets Manager + External Secrets Operator
- **인증 토큰**
  - access 토큰 15분, refresh 토큰 14일
  - refresh 토큰은 사용할 때마다 재발급
- **배포**
  - GitHub Actions OIDC로 임시 권한 발급 (장기 키 없음)
  - ECR에 이미지 게시
  - 프라이빗 서브넷 runner(t3.small)에서 kustomize로 배포
  - 커밋 SHA 태그, rolling update
- **테스트**
  - CI 자동 테스트 약 3,000건 통과 시 배포
  - AI 파이프라인 약 1,380건, 문서 서비스 약 980건, 프론트엔드 약 700건
- **모니터링과 알림**
  - 로그: Fluent Bit → CloudWatch, 14일 보관
  - 알림: SNS → Lambda → Discord (장애, 비용)
  - 전송 실패한 알림은 SQS에 보관

**주요 기능**

- **Wiki 생성(Ingest)**
  - PDF/Markdown에서 핵심 개념과 관계를 추출해 Wiki 생성
  - 모든 내용에 원문 근거 연결
  - 기존 Wiki의 같은 개념은 병합
  - PDF: 오픈소스 도구로 1차 변환 → 원본과 대조 → 표/수식 AI 복원
- **자연어 질의응답(Query)**
  - 키워드 검색 + 의미 검색으로 원문 인용 답변
  - 근거가 부족하면 웹 검색으로 보완 (사용자 허용 시)
  - 답변을 Wiki 지식으로 편입
- **문서 편집 Agent와 Skill**
  - 자연어 요청으로 문서 생성/편집, 폴더 정리
  - 저장 전 사용자 확인
  - 반복 작업은 Skill로 저장, 시험 실행으로 미리 확인
- **Wiki 유지보수(Lint)**
  - 원본 수정/삭제 시 관련 Wiki 재검토
  - 끊긴 참조 정리
  - 개념 승격, 병합, 분리
- **로그와 복원**
  - AI 작업별 실행 시점, 상태, 변경 대상 기록
  - 단일 또는 일괄 되돌리기
  - 복원 내역도 새 기록으로 저장
- **자료 이전과 연동**
  - Notion 가져오기: 폴더 구조, 본문, 이미지, 표, PDF
  - MCP: Codex/Claude Code에서 검색과 편집 → 웹에서 승인 후 반영
- **음성(STT/TTS)**
  - 음성 질문 → 텍스트 변환 → Agent 실행, 답변은 음성으로 재생
  - 실시간 회의 전사, 긴 녹음 분할 전사 → 회의록 초안

### 팀 평가 결과 (최종)

직접 작성하고 팀 전원이 검수한 평가셋 397건으로, 모든 사례를 3회씩 실행했습니다.

| 지표 | Fruition | 일반 RAG |
| --- | --- | --- |
| 질의응답 정답 | 279/300 (93.0%) | 246/300 (82.0%) |
| 오답 | 3/300 (1.0%) | 22/300 (7.3%) |
| 인용 적합성 | 229/240 (95.4%) | 186/240 (77.5%) |
| 근거 없는 주장 | 13/701 (1.9%) | 36/734 (4.9%) |
| 평균 응답 시간 | 5.5초 | 4.3초 |

- **Ingest**: 개념 병합/연결 판정 94.3%, 원문 근거 적합성 92.5%였습니다.
- **편집/관리**: 문서 편집 88.9%, 폴더 정리 98.3%, Skill 시험 실행 77.8%였습니다.
- **Lint**: 문서 편입을 마친 워크스페이스 12개에서 모두 성공했고 끊긴 참조는 0건이었습니다.
- **PDF 변환**: 공개 PDF 15개(115쪽) 기준 제목 97.6%, 본문 96.1%, 표 셀 99.3%, 수식 100%, 이미지 91.3%를 복원했습니다.

LLM Wiki를 중심으로 범위를 좁히고, AI 작업이 몰려도 멈추지 않는 구조와 예산 안의 인프라를 직접 설계/운영한 결과, 문서 편입부터 질의응답/편집/유지보수/복원까지 이어지는 서비스를 웹 SaaS로 완성하고 베타 테스트까지 진행했습니다.\
핵심 기능으로 소프트웨어 저작권을 등록하고 임시 특허를 출원했습니다(2026.11).\
멘토단으로부터 "짧은 개발 기간에도 상용 서비스 수준의 완성도를 확보함", "AI Agent의 신뢰성 문제를 원문 근거 연결, 사용자 승인, 감사 로그와 작업 단위 롤백 같은 아키텍처적 접근으로 해결함"이라는 평가를 받았습니다.
