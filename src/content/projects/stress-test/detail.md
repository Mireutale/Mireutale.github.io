## 실험 목적

수강신청처럼 요청이 몰릴 때 과부화 된 서버가 멈추는 상황을 재현하고, 몰린 요청을 큐에 넣고, 서버의 동시 처리 수를 조절하여 요청을 처리할 수 있는지 확인하고자 하였습니다.

## 구현과 비교 조건

요청은 k6 → WebFlux 라운드로빈 로드밸런서(:8080) → 서버 3대(:8081\~8083) → PostgreSQL 순서로 처리합니다.\
DB 락 경합을 관찰하기 위해서 세 서버가 DB 하나를 공유하도록 구성했습니다.

동시 처리 수를 고정하는 방식과, 응답 지연을 보고 서버의 여유를 확인해서 동시 처리 수를 늘리고 과부하가 감지되면 줄이는 적응형 방식 2가지를 비교했습니다.

수강 등록 API에 **60초 동안 초당 2,000건**의 요청을 보냈고.\
VU는 1,000\~5,000, 통과 기준은 p95(95%의 응답에 대한 평균 처리 시간) 500ms 미만·실패율 1% 미만으로 두었습니다.

## 측정 결과

| 지표 | 고정 동시성 | 적응형 동시성 |
| --- | --- | --- |
| 실패율 | 20.79% | **0%** |
| p95 응답 시간 | 11.71s | **462ms** |
| 처리량 | 초당 1,221건 | **초당 1,982건** |
| 통과 기준 | 미달 | **통과** |

- 초당 200건에서는 p95 21ms·실패율 0%였습니다.\
  조회 API는 VU 100에서 p95 27ms로 초당 878건을 처리했습니다.
- 정원 100명인 강좌에 요청을 집중시켜도 DB의 수강 인원은 정확히 100명으로 유지됐습니다.

## 측정 오류 해결과 한계

부하를 더 높이면 큐를 키우는 것만으로는 부족했습니다.\
초당 1만 명 조건에서 큐 용량과 동시 처리 수를 10배로 늘려도 실패율은 84.47%에서 77.84%로 줄어드는 데 그쳤고, 실패율 0%는 위의 초당 2,000건 조건에서 얻은 결과이며, 더 큰 부하에서는 처리 역량과 유입량을 함께 조절해서 재 평가해야 합니다.
