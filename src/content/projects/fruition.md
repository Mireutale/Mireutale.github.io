## 배경

PDF, 워드, 노션, 메모 앱에 자료를 저장해도 나중에 어디에 뒀는지 기억나지 않는 경우가 있습니다. 내용은 어렴풋이 기억하지만 파일 이름을 몰라 찾지 못하는 문제를 해결하고 싶었습니다. 자료를 많이 모으지만 정리는 미루는 대학생·대학원생을 초기 사용자로 정했습니다.

자료 사이의 관계도 함께 정리하기 위해 **LLM Wiki** 방식을 택했습니다. 새 자료가 들어오면 기존 위키와 비교해 관련 항목을 연결하고 내용을 수정하거나 새 항목을 만듭니다.

## 구조와 구현

![Fruition AWS 인프라 구성도](/img/fruition/architecture.png)

- **아키텍처**: 서울 리전 VPC(가용영역 2개)에 EKS 1.35 프라이빗 클러스터를 구성하고 도메인별 namespace로 나눈 MSA를 배포했습니다. 인증·워크스페이스·권한을 맡는 access-svc(:8081)와 문서·채팅·Wiki·AI 게이트웨이를 맡는 document-svc(:8080)는 서비스와 RDS(PostgreSQL 16)를 각각 분리했습니다. AI 파이프라인(pipeline-api, ingest·query·agent 워커, converter, edit-event-consumer, pipeline-agent-worker, BGE-M3 embedding-server)은 Kafka(Strimzi, mTLS) 토픽으로 비동기 연결했고 Next.js 프론트엔드는 같은 클러스터의 Fargate에 Pod 2개로 배포했습니다.
- **노드 구성**: 일반 노드그룹은 t3.large 온디맨드 2\~5대(평소 2\~4대, 5번째는 배포할 때만 사용)입니다. AI 워커는 m5·m6i·m7i xlarge 스팟 0\~4대에 taint를 걸어 AI 작업만 배치되게 했습니다. 서비스는 HPA, 워커는 KEDA로 확장하고 노드는 태그 범위로 권한을 제한한 Cluster Autoscaler가 조정합니다.
- **절전·기동**: 실행 중인 작업이 없을 때 절전 모드로 전환하면 두 노드그룹을 0대로 줄이고 ASG Launch를 중지해 노드가 다시 생성되지 않게 했습니다. 화면은 Fargate에서 실행되므로 절전 중에도 응답하고 사용자가 로그인하기 전에 EventBridge로 기동 이벤트를 보내면 request-wake Lambda가 일반 노드 2대와 AI 노드 1대를 깨웁니다. 1분마다 ALB 5XX를 확인하는 감지는 예비 경로로 두었습니다. 상태를 DynamoDB에 먼저 기록하므로 중간에 실패해도 다음 실행에서 이어서 복구합니다. 화면에는 기동 이벤트를 보내는 권한만 줘 키가 탈취되더라도 절전 상태를 조작할 수 없게 했습니다.
- **네트워크·보안**: 외부 진입 경로는 사용자 → WAF → ALB 하나뿐입니다. ALB에서 TLS를 종료합니다. HTTP 요청은 443으로 리다이렉트하고 경로·호스트에 따라 라우팅합니다. WAF에는 AWS 관리형 규칙(IP 평판, 공통 규칙, 알려진 악성 입력, SQLi)과 내부 경로(/internal, Swagger) 차단, 접근 코드 검사, IP당 5분 3,000건·/api/ 전체 5분 6,000건 제한을 적용했습니다. 외부 LLM 호출과 이미지 pull은 NAT 게이트웨이 1대로 나가는 트래픽만 허용했고 EKS API는 프라이빗 전용으로 두어 배포 러너에서만 443으로 접근할 수 있게 했습니다. VPC Flow Log도 기록합니다.
- **데이터**: 인증 DB는 Multi-AZ로, 문서·AI 데이터를 담은 코어 DB는 비용을 고려해 Single-AZ로 두었습니다(둘 다 SSL 강제, 암호화, 7일 백업, 삭제 보호). Redis 7.1은 2노드 Multi-AZ 자동 장애조치 구성에 TLS를 필수로 적용하고 기본 사용자를 비활성화한 뒤 서비스별 ACL 계정으로 쓸 수 있는 키와 명령을 제한했습니다. S3에는 KMS CMK 암호화와 버전 관리를 적용하고 TLS 연결만 허용했습니다. 파드는 IRSA로 서비스별 경로 권한만 받아 게이트웨이 엔드포인트로 전송합니다(tmp/는 7일 뒤 정리).
- **시크릿·IaC**: DB 계정, Redis, JWT 키는 Secrets Manager(KMS 암호화)에 두고 External Secrets Operator가 쿠버네티스 시크릿으로 동기화합니다. VPC·EKS·RDS·WAF 같은 AWS 리소스는 Terraform으로 관리하고 ACM 인증서와 외부 DNS(Dynu)만 Terraform 밖에서 연결했습니다.
- **CI/CD**: GitHub Actions는 OIDC로 IAM 역할을 받아 쓰므로 저장소에 장기 자격 증명을 두지 않습니다. 이미지 게시 역할은 main 브랜치에서만, 배포 역할은 feedback 환경에서만 쓸 수 있습니다. main에 병합되면 ECR 저장소 5개에 이미지를 푸시하고(태그 불변, 푸시 시 취약점 스캔, 최근 60개 보관), feedback 환경은 프라이빗 서브넷의 자체 호스팅 러너(t3.small, SSM 접속)에서 kustomize로 커밋 SHA 기준으로 rolling update를 수행합니다.
- **운영·비용**: 컨테이너 로그(14일 보관)와 메트릭은 Fluent Bit로 CloudWatch에 수집합니다. 파드·노드 CPU와 메모리, 실패 노드와 지표 누락, RDS CPU·저장 공간, Redis 메모리, ALB 5XX·지연·요청 수, WAF 차단, NAT 송신량에 알람을 걸어 SNS → Lambda → Discord로 알림을 받습니다. 알림 전송이 실패하면 SQS에 보관하고 이 실패도 알람으로 받습니다. AWS 비용이 월 400·550·650달러를 넘을 때도 같은 경로로 알림을 받습니다.
- **프론트엔드**: 디자이너와 함께 화면 구조와 사용자 흐름을 정하고 Next.js·React·TypeScript로 구현했습니다. 코드는 도메인과 기능별로 나누고 API 통신·상태 관리·UI 컴포넌트를 분리했습니다. GFM 마크다운 편집기와 지식 그래프 뷰를 만들고 채팅 답변을 선택해 Wiki에 추가할 수 있게 했습니다.
- **신뢰성 설계**: 원문은 그대로 보존하고 Wiki 항목마다 원문 근거를 연결했습니다. AI 작업은 위험도에 따라 자동 실행, 사후 검토, 사전 승인으로 나눴습니다. 모든 작업은 append-only 로그로 남기며 스냅샷과 diff로 한 번에 되돌릴 수 있습니다. 복원할 때도 기존 기록을 지우지 않고 새 기록을 추가합니다.

## MSA 전환 근거 (k6 부하 비교)

모놀리스(dev)와 MSA(dev-msa)에서 같은 k6 시나리오를 실행한 결과로 전환 여부를 결정했습니다. 로컬 머신 한 대에서 mock LLM으로 측정한 상대 비교입니다.

| 시나리오 | 모놀리스 | MSA |
| --- | --- | --- |
| 평상시 (VU 10→50→100, 8분 × 2회) | 초당 218.9건 · 실패 0% · p95 22.6ms | 초당 217.4건 · 실패 0% · p95 22.2ms |
| AI 요청 폭주 (AI 100 VU + 일반 20 VU) | 일반 API 실패율 26.45% · 인증 응답 중앙값 9,981ms · 로그인 불가 | 일반 API 실패율 16.67% · 인증 응답 중앙값 7.15ms · 로그인 83ms |
| 10분짜리 AI 작업 30건 동시 실행 | 22건 접수 후 모두 실패 | 30건 모두 접수 · 실패 0 · 워커 6대가 차례로 처리 |

- **판단**: 평상시에는 거의 차이가 없었고 문서 상세·생성은 오히려 MSA가 3\~8ms 느렸습니다. 하지만 AI 요청이 몰리자 모놀리스는 Tomcat 스레드가 모두 점유되어 인증부터 문서까지 전부 멈췄고 MSA는 문서 서비스만 느려졌을 뿐 인증은 정상적으로 동작했습니다. 이 차이를 근거로 MSA로 전환했습니다.
- **원인 분석**: 모놀리스에서 긴 작업이 실패한 원인은 두 가지였습니다. @Transactional 안에서 LLM 응답을 기다리는 동안 DB 커넥션을 계속 점유해 HikariCP 풀이 고갈됐습니다. 코드에 하드코딩된 5분 타임아웃도 작업을 중단시켰습니다. MSA에서는 Kafka 기반 비동기 실행과 전용 워커로 분리해 해결했습니다.
- **장애 격리 확인**: access-svc를 의도적으로 중단해도 권한 캐시(TTL 300초) 덕분에 문서 조회(200)와 생성(201)은 정상 처리됐습니다.

## 담당 작업

- **팀장**: 마일스톤과 배포 일정을 관리하고 사용자·멘토 의견을 수집했습니다. 팀원들과 의견을 검토해 기능 우선순위와 설계를 조정했습니다.
- **범위 조정**: 기획심의에서 "MVP가 너무 넓다"는 피드백을 받고 LLM Wiki 자동 생성과 자연어 검색부터 만들기로 했습니다. 두 기능을 PoC로 확인한 뒤 나머지 기능의 우선순위를 정했습니다. 파싱이 까다로운 PDF는 1차 범위에서 제외하고 텍스트·마크다운을 먼저 지원한 뒤 Converter로 확장하도록 일정을 잡았습니다.
- **AI 개발 환경**: 팀 개발 규칙과 프로젝트 맥락을 문서로 정리해 AI 도구가 참고하도록 했습니다. 반복 작업은 공용 스킬로 공유했고 AI가 만든 코드도 리뷰와 테스트를 통과해야 반영했습니다.
- **개발 분담**: 아키텍처 설계와 AWS 인프라 운영, 배포 자동화, 프론트엔드 개발은 제가 맡았습니다. Ingest·Lint 파이프라인과 평가 체계는 AI 담당 팀원이 설계하고 구현했습니다.

## 결과 (중간 평가)

- **Ingest**: 1,189줄 분량의 설계 문서를 181개 구간으로 나눠 3회 평가했고 의미와 핵심 개념 보존 점수는 4.67/5였습니다.
- **Query**: Wiki 항목 77개·질문 120개 기준으로 Top-1 정확도 83.78%, Top-10 90.99%였고 Wiki에 답이 있는 12건은 인용이 모두 일치했습니다.
- **기능 평가**: 편집 Agent 82.46%, 문서 관리 95.24%, Skill 87.5%를 통과했습니다. 로그·복원 기능은 중복 실행 방지와 워크스페이스 격리까지 통합 테스트를 통과했습니다.
- **자동 테스트**: AI 파이프라인 약 1,380건, 문서 서비스(Java) 약 980건, 프론트엔드 약 700건을 CI에서 통과해야 배포됩니다.
- **임베딩**: BGE-M3로 질문 1건을 임베딩하는 데 14ms(초당 약 70건), 개념 후보 100건을 한 번에 처리하는 데 0.4초가 걸렸습니다. AI 노드와 같은 4 vCPU 개발 환경에서 측정했습니다.
- **멘토 평가**: "원문 불변 저장·근거 연결·스냅샷 롤백을 설계 단계부터 반영해 AI Agent 신뢰성을 아키텍처 레벨에서 다룸", "3인 팀 대비 FE·BE·AI 전 영역 산출물이 고르게 갖춰짐".
