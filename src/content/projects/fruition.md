## 해결하려던 문제

PDF, 워드, 노션, 메모 앱에 자료를 모아도 내용만 어렴풋이 기억나 정작 필요할 때 찾지 못하는 문제에서 출발했습니다. 초기 사용자는 자료를 많이 모으지만 정리는 미루는 대학생·대학원생으로 정했습니다.

새 자료가 들어오면 기존 위키와 비교해 관련 항목을 연결하고 내용을 갱신하는 **LLM Wiki** 방식을 택했습니다.

## 내가 맡은 부분

- **팀장·기획**: 마일스톤과 배포 일정을 관리했습니다. 기획심의의 "MVP가 너무 넓다"는 의견을 반영해 LLM Wiki 생성과 자연어 검색부터 만들고, PoC 이후 나머지 기능의 순서를 정했습니다. PDF는 텍스트·마크다운 지원 이후 Converter로 확장하도록 범위를 조정했습니다.
- **아키텍처**: 모놀리스와 MSA를 k6로 비교하고 인증과 문서 서비스를 분리했습니다. AI 작업은 Kafka 기반 비동기 실행과 전용 워커로 분리했습니다.
- **프론트엔드**: 디자이너와 화면 구조를 정하고 Next.js·React·TypeScript로 GFM 편집기, 지식 그래프 뷰, 채팅 답변을 Wiki에 추가하는 기능을 만들었습니다.
- **인프라·배포**: Terraform으로 AWS EKS 인프라를 구성하고 GitHub Actions OIDC 배포를 자동화했습니다. 인증 DB·Redis 이중화, 절전·자동 기동, 모니터링과 비용 알림을 구현했습니다.
- **AI 개발 환경**: 팀 공통 개발 규칙과 프로젝트 맥락을 문서로 정리하고 반복 작업은 공용 스킬로 공유했습니다. AI가 만든 코드도 리뷰와 테스트를 통과해야 반영했습니다.

Ingest·Lint 파이프라인과 AI 평가 체계는 AI 담당 팀원이 설계하고 구현했습니다. 아래 AI 평가 수치는 팀 전체 결과입니다.

## 문제 해결과 검증

### AI 요청이 몰리면 로그인까지 멈추는 문제

모놀리스(dev)와 MSA(dev-msa)를 로컬 머신 한 대에서 mock LLM과 같은 k6 시나리오로 비교했습니다. 평상시에는 가상 사용자(VU)를 10→50→100명으로 늘렸고, 요청 폭주 시에는 AI 100 VU와 일반 API 20 VU를 동시에 실행했습니다. 운영 환경의 절대 성능이 아닌 두 구조의 상대 비교입니다.

| 시나리오 | 모놀리스 | MSA |
| --- | --- | --- |
| 평상시 (VU 10→50→100, 8분 × 2회) | 초당 218.9건 · 실패 0% · p95 22.6ms | 초당 217.4건 · 실패 0% · p95 22.2ms |
| AI 요청 폭주 (AI 100 VU + 일반 20 VU) | 일반 API 실패율 26.45% · 인증 응답 중앙값 9,981ms · 로그인 불가 | 일반 API 실패율 16.67% · 인증 응답 중앙값 7.15ms · 로그인 83ms |
| 10분짜리 AI 작업 30건 동시 실행 | 22건 접수 후 모두 실패 | 30건 모두 접수 · 실패 0 · 워커 6대가 차례로 처리 |

모놀리스는 AI 작업이 Tomcat 스레드를 모두 점유하면서 인증까지 막혔습니다. 긴 작업에서는 @Transactional 안에서 LLM 응답을 기다리는 동안 HikariCP 풀이 고갈됐고, 하드코딩된 5분 타임아웃도 작업을 중단시켰습니다.

인증과 문서 서비스를 나누고 AI 작업은 Kafka와 전용 워커로 넘겼습니다. 평상시 문서 상세·생성은 MSA가 오히려 3\~8ms 느렸고 일반 API 실패도 남았지만, AI 부하가 몰려도 인증 응답을 유지하는 차이를 보고 MSA로 전환했습니다. access-svc를 중단한 별도 실험에서도 권한 캐시(TTL 300초) 덕분에 문서 조회(200)와 생성(201)이 정상 처리됐습니다.

### 월 예산 안에서 가용성과 비용 조정

월 예산은 400\~650달러였습니다. 로그인이 막히면 서비스를 쓸 수 없어 인증 DB는 Multi-AZ, Redis 7.1은 자동 장애조치가 가능한 2노드로 구성했습니다. 문서·AI 코어 DB는 테스트 단계라 Single-AZ로 두고 실제 사용자 데이터를 받기 전에 Multi-AZ로 전환하기로 했습니다.

NAT 게이트웨이는 1대, AI 워커는 스팟 노드를 사용했습니다. 실행 중인 작업이 없을 때 절전 모드로 전환하면 일반·AI 노드그룹을 0대로 줄이고, Fargate에 남겨 둔 화면에서 접속을 받아 다시 기동합니다. EventBridge → request-wake Lambda가 일반 노드 2대와 AI 노드 1대를 기동하며, 상태를 DynamoDB에 기록해 중간 실패 시 다음 실행에서 복구하도록 했습니다.

### AI가 바꾼 내용을 확인하고 되돌리기

원문은 보존하고 Wiki 항목마다 근거를 연결했습니다. AI 작업은 위험도에 따라 자동 실행·사후 검토·사전 승인으로 나누고 append-only 로그와 스냅샷·diff로 되돌릴 수 있게 했습니다. 복원도 새 기록으로 남깁니다.

## 시스템 구성

![Fruition AWS 인프라 구성도](/img/fruition/architecture.png)

- **컴퓨팅**: 서울 리전의 가용영역 2개에 EKS 1.35 프라이빗 클러스터를 구성했습니다. access-svc와 document-svc는 서비스·RDS(PostgreSQL 16)를 각각 분리하고 Next.js는 Fargate Pod 2개로 배포했습니다.
- **확장**: 일반 노드는 t3.large 온디맨드, AI 노드는 m5·m6i·m7i xlarge 스팟을 사용했습니다. 서비스는 HPA, 워커는 KEDA, 노드는 Cluster Autoscaler로 조정합니다. AI 노드에는 taint를 적용했습니다.
- **네트워크·데이터**: WAF → ALB로 외부 요청을 받고 EKS API는 프라이빗으로 제한했습니다. RDS·Redis·S3에 암호화와 TLS를 적용하고 서비스별 Redis ACL·S3 IRSA 권한을 나눴습니다. 시크릿은 Secrets Manager와 External Secrets Operator로 관리합니다.
- **배포·운영**: GitHub Actions는 OIDC로 IAM 역할을 받아 ECR에 이미지를 게시하고 프라이빗 서브넷의 러너에서 kustomize로 커밋 SHA 기준 rolling update를 수행합니다. Fluent Bit·CloudWatch로 로그와 지표를 모으고 SNS → Lambda → Discord로 장애·비용 알림을 받습니다. 알림 실패는 SQS에 보관하며 월 400·550·650달러 비용 알림도 설정했습니다.

## 팀 평가 결과 (중간 평가)

- **Ingest**: 1,189줄 설계 문서를 181개 구간으로 나눠 3회 평가했습니다. 의미와 핵심 개념 보존 점수는 4.67/5였습니다.
- **Query**: Wiki 항목 77개·질문 120개 기준 Top-1 정확도 83.78%, Top-10 90.99%였습니다. Wiki에 답이 있는 12건은 인용이 모두 일치했습니다.
- **기능 평가**: 편집 Agent 82.46%, 문서 관리 95.24%, Skill 87.5%를 통과했습니다. 로그·복원은 중복 실행 방지와 워크스페이스 격리까지 통합 테스트를 통과했습니다.
- **배포 검증**: AI 파이프라인 약 1,380건, 문서 서비스(Java) 약 980건, 프론트엔드 약 700건의 자동 테스트를 CI에서 통과해야 배포됩니다.
- **임베딩**: AI 노드와 같은 4 vCPU 개발 환경에서 BGE-M3 질문 임베딩은 1건 14ms(초당 약 70건), 개념 후보 100건 일괄 처리는 0.4초였습니다.
- **멘토 평가**: "원문 불변 저장·근거 연결·스냅샷 롤백을 설계 단계부터 반영해 AI Agent 신뢰성을 아키텍처 레벨에서 다룸", "3인 팀 대비 FE·BE·AI 전 영역 산출물이 고르게 갖춰짐".
